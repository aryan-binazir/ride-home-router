# Route session edit orchestration

Browser boot previously coordinated the Route session orchestrator with a separate participant move batcher. Every manual edit knew its endpoint, request headers, requested session attribution and result installation. Save and Route editor callers separately flushed the queue. This spread the ordering rules across the browser adapters.

Deepen `createRouteSessionOrchestrator` in `event-planner.js`. It privately owns the move queue, debounce, batch limit, serial manual actions, pending session tracking, fetch dispatch, response attribution, installation and Save after pending edits. Its production interface accepts move, swap, reset, add, timings, editor and Save actions. Browser adapters read controls, validate forms, request confirmation and render button state. They no longer construct edit requests or coordinate flushing.

Keep Plan eligibility in `createPlannerState`. The edit owner checks that state before sending each queued request. It separately reads the installed DOM session identity when deciding whether successful response HTML still belongs to the displayed routes. A Plan change discards queued edits for the state's session and resolves canceled manual callers with false. It does not cancel an in-flight edit. That edit may still install into the same displayed session while the Plan remains stale. Successful old-session responses count as handled but cannot replace another session. Errors still report even if the requested session is no longer installed.

Preserve the 500ms move debounce, 64-move batch limit, single and multiple move payloads and serial order around manual actions. A failed action stops that queue run; remaining work keeps the existing rescheduling and session outcome rules. Save reads Plan eligibility and asks the browser adapter to report any blocked reason. It suppresses duplicate waits, waits for its own session and finds the matching live enabled Save form after installation. Any failure in that session's flush prevents Save even if subsequent batches succeed. Opening the Route editor waits for moves and rechecks eligibility and installed identity. Submitting its move uses the same queue. `editors.js` retains ownership of transient editor generations and stale HTMX swaps.

The existing installer preserves measured timings for unchanged itineraries and user-entered date and notes on full renders. Fragments preserve untouched DOM elements and the Save form. Pending edits lock copy, preview and Save until the current session settles. The owner reports pending changes so browser boot can render those affordances.

Tests exercise the production edit interface and production scripts with real DOM elements and the production stylesheet in Chromium at 390px and 1440px. They check editor containment and native HTMX Save interception before the edit queue settles. The existing handler fixture covers real HTMX editor loading, searching and submitting across 500 routes. No server protocol, Plan selection, restore or calculation policy changes are required. A generic command framework or forwarding module would expose the coordination this owner is meant to hide.
