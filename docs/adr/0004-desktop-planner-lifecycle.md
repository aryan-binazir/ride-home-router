# Desktop planner lifecycle ownership

The desktop planner decides whether installed routes still belong to the current inputs. Previously its state reducer owned current, stale and saved status, while browser boot separately held request fingerprints, calculation generations, restore cancellation and active-session storage. Calculate, restore, input-change and Clear All listeners had to coordinate those pieces before eligibility could be trusted.

Deepen `createPlannerState` in the existing script. It owns that state together, using the existing fingerprint reader and change notification plus a best-effort storage collaborator. Calculation requests retain their individual identity across overlapping calculate and capacity requests. A result consumes its request attribution; an unknown result remains stale. Clear All invalidates outstanding calculations and aborts restore, while calculation and restore starts only abort restore. These operations deliberately preserve the existing asymmetric invalidation rules.

A restore returns a handle for its fetch signal, result adoption and finalization. The handle retains the requested fingerprint, including legacy fallback to the restored draft. Finalization still unconditionally releases restore tracking. This preserves the existing behavior when an older aborted restore finalizes after another start; redesigning that behavior is outside this refactor. AbortController and fetch retain responsibility for preventing aborted response delivery.

The route-session orchestrator still reads the installed DOM pane's session ID when deciding whether edit HTML can replace it. Planner state answers eligibility and savedness. Those identities answer different questions, so combining them would break old-result ownership checks. The existing move queue, result installer and save-after-flush sequence remain intact.

Browser boot translates DOM inputs and HTMX events, renders affordances, discards pending moves on state changes, persists the form draft and retains user date/notes across renders. It no longer owns active-session keys, generation counters, request maps or restore fingerprints/controllers. Storage keys, formats, legacy fallback and saved-session reversion remain unchanged. Lifecycle tests use the same request and restore interface as production; existing DOM and HTMX regressions remain the adapter coverage. No loader, mobile or server changes are required.
